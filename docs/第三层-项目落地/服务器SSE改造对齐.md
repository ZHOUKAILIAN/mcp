# 服务器 SSE 改造对齐

## 1. 文档目的

本文用于记录将两个 MCP 从当前本地 `stdio` 使用方式改造成服务器 SSE 服务的范围、执行结果、风险和验收标准。服务器部署已按单用户私人服务范围完成可安全完成部分；天气服务因缺少真实 APPCODE 暂未启动。

## 2. 当前状态

### 2.1 客户端使用方式

按照当前实际使用方式，MCP 客户端仍通过 `stdio` 连接服务：

```text
MCP 客户端
  -> 本地启动 MCP 子进程
  -> 通过 stdio 通信
```

用户需要在本地安装依赖，并在本地启动 MCP 服务。

### 2.2 仓库代码状态

两个服务的源码已经包含 HTTP SSE 启动入口：

```text
GET  /mcp
POST /mcp-messages
```

默认端口：

```text
天气 MCP：7777
小蚕 MCP：7788
```

生产启动脚本、只监听本机和服务部署配置已完成；天气服务尚待真实 APPCODE，小蚕远程 SSE 已完成初始化级验证。

## 3. 目标状态

目标是两个 MCP 都部署在服务器上，由 MCP 客户端通过 HTTPS SSE 地址连接：

```text
MCP 客户端
  -> HTTPS
  -> 域名
  -> 反向代理
  -> MCP 服务进程
  -> SSE 通信
```

用户最终不再需要：

- 在本地安装这个仓库。
- 在本地启动 MCP 子进程。
- 为每个 MCP 维护本地启动命令。

建议的服务地址形式：

```text
https://weather.example.com/mcp
https://xiaocan.example.com/mcp
```

实际域名和路径以后以服务器配置为准。第一阶段建议使用两个独立子域名，避免两个服务共用路径时产生消息地址映射问题。

## 4. 需要对齐的三个核心问题

### 问题一：天气上游请求关闭了 TLS 证书校验

文件：

```text
packages/weather-mcp/src/api/request.ts
```

当前存在：

```ts
process.env.NODE_TLS_REJECT_UNAUTHORIZED = "0";
```

这会让 Node.js 在访问天气上游 HTTPS 接口时不校验证书，无法确认请求确实到达可信的上游服务器。

#### 风险

- 中间人可以伪造或篡改响应。
- 上游身份无法得到可靠验证。
- 服务器启动或请求时可能出现安全警告。
- 这是全局进程设置，影响该进程内其他 HTTPS 请求。

#### 对齐结论

当前先保留这行代码作为天气接口的兼容性例外，不把它当作 Node 不支持证书校验。实际检查结果显示：

- `https://ssch.api.moji.com` 的证书校验可以通过。
- `https://aliv18.data.moji.com` 返回的证书主体是 `*.alicloudapi.com`，与访问域名不匹配。
- Node.js 22 会对此返回 `ERR_TLS_CERT_ALTNAME_INVALID`。

因此，问题更可能是上游接口证书配置或域名配置不匹配，而不是 Node.js 不支持 HTTPS 证书。当前全局关闭校验虽然能绕过问题，但会影响进程内所有 HTTPS 请求，风险较大。

#### 当前处理决定

- 第一阶段服务器部署先不强制删除该兼容逻辑，优先保证天气服务可用。
- 不再把它解释为“Node 不支持证书”。
- 后续应将绕过逻辑限制到确实存在问题的单个上游请求，不能继续使用全局关闭方式影响所有请求。
- 同时保留上游证书不匹配的记录，未来上游修复后应恢复正常校验。

#### 验收标准

- 文档明确记录这是上游证书域名不匹配的兼容例外。
- 兼容逻辑不会扩大到无关的 HTTPS 请求。
- `ssch.api.moji.com` 在正常证书校验下请求成功。
- 上游请求失败时记录明确错误，不能静默吞掉证书问题。

### 问题二：当前启动命令是开发监听模式

两个软件包当前的启动命令都是：

```json
"start": "tsx --watch src/index.ts"
```

其中 `--watch` 会持续监听源代码变化，并在文件变化时自动重启服务。

#### 为什么不适合作为生产启动方式

- 生产服务不需要监听源代码。
- 部署目录发生无关文件变化时可能意外重启。
- 版本、构建产物和回滚边界不够清晰。
- 服务器进程行为混入开发模式逻辑。
- 不利于使用固定构建产物进行发布。

#### 对齐结论

保留开发命令和生产命令的区分：

```text
开发：自动监听，方便改代码
生产：固定版本启动，不监听源代码
```

建议目标命令：

```json
{
  "scripts": {
    "dev": "tsx --watch src/index.ts",
    "build": "tsc",
    "start": "node dist/index.js"
  }
}
```

具体是否采用 `dist` 构建目录，需要结合当前 TypeScript 配置验证后确定。第一阶段也可以先使用不带 `--watch` 的 `tsx src/index.ts`，但正式长期运行更建议使用编译后的 JavaScript。

#### 验收标准

- 生产启动命令不包含 `--watch`。
- 生产服务由 systemd、Docker 或其他固定进程管理方式托管。
- 生产启动使用明确的版本和配置。
- 服务重启、停止、日志和回滚方式已经明确。

### 问题三：从本地 stdio 切换到服务器 SSE

当前代码已经包含 HTTP SSE 入口，但“代码有 SSE 入口”和“客户端可以稳定远程使用 SSE”不是一回事。

#### 当前链路

```text
MCP 客户端
  -> stdio
  -> 本地 MCP 服务
```

#### 目标链路

```text
MCP 客户端
  -> HTTPS SSE 地址
  -> 服务器反向代理
  -> MCP 服务
```

#### 必须完成的工作

1. 确认两个服务的 `/mcp` 和 `/mcp-messages` 通信正常。
2. 为两个服务配置固定生产启动方式。
3. 服务器配置域名和 HTTPS 证书。
4. 增加客户端身份验证，不能把 MCP 端口裸露到公网。
5. 检查反向代理是否正确支持 SSE 长连接和消息转发。
6. 修复当前每个服务只保存一个共享传输层引用的问题。
7. 明确服务是单用户还是多用户；第一阶段按单用户私人服务处理。
8. 将 MCP 客户端配置从本地 `stdio` 命令切换为远程 SSE 地址。
9. 验证断线重连、重复请求、服务重启和错误返回。

#### 当前代码的连接限制

两个服务当前都使用类似的全局传输层引用：

```ts
private transport: Transport | null = null;
```

这意味着后建立的连接可能覆盖先建立的连接。当前实现更适合：

```text
单用户
单客户端
单服务进程
```

不能直接按多用户公共服务理解。

#### 验收标准

- MCP 客户端可以仅凭远程 SSE 地址连接天气服务。
- MCP 客户端可以仅凭远程 SSE 地址连接小蚕服务。
- 不需要在客户端机器上执行 `pnpm start:*`。
- SSE 长连接不会被反向代理错误缓冲或主动断开。
- 消息请求可以正确回到对应的会话。
- 未授权请求无法调用 MCP 工具。
- 服务重启后有明确的重连行为。

## 5. 第一阶段建议范围

为了降低风险，第一阶段不做多用户平台，采用以下范围：

```text
两个独立 MCP 服务
单用户
私人服务器
HTTPS
客户端身份验证
固定进程管理
SSE 远程接入
```

暂不包含：

- 多用户账号体系。
- 多租户数据隔离。
- 多实例共享 JSON 文件。
- 公共开放注册。
- 未经确认的小蚕接口公共代理。

## 6. 推荐实施顺序

### 阶段一：代码安全和生产启动

- 保留天气接口当前已确认的 TLS 兼容逻辑；后续如上游修复证书域名不匹配，再将绕过范围收窄到单个请求并恢复正常校验。
- 清理测试脚本中的真实 AppCode。
- 区分开发启动和生产启动。
- 验证 `pnpm typecheck` 和生产启动命令。

### 阶段二：服务器基础部署

- 准备服务器运行环境。
- 部署两个 MCP 服务。
- 配置环境变量和受保护的运行数据目录。
- 使用 systemd、Docker 或其他固定方式托管进程。
- 仅监听服务器本机端口，不直接暴露 Node 端口。

### 阶段三：域名和 HTTPS

- 配置两个域名或两个子域名。
- 配置 HTTPS 证书。
- 配置反向代理的 SSE 长连接参数。
- 配置访问身份验证。

### 阶段四：远程客户端接入

- 将客户端配置从 `stdio` 改为 SSE 地址。
- 先验证天气 MCP。
- 再验证小蚕 MCP。
- 验证连接、工具调用、断线重连和服务重启。

### 阶段五：生产化增强

- 按会话管理传输层。
- 增加健康检查、限流和结构化日志。
- 明确小蚕凭据和运行数据的备份、轮换和恢复方案。
- 如果未来支持多用户，再设计数据库、租户和凭据隔离。

## 7. 服务器检查与部署前提

部署前只读检查记录：

- 系统：Ubuntu 24.04 LTS，Node.js `v22.22.0`，pnpm `10.29.2`。
- Nginx 已安装并运行，`80`、`443` 已被现有站点使用；`7777`、`7788` 当时无监听。
- 现有 Halo、OpenClaw、`blog.zhoukailian.wiki`、`zhoukailian.wiki` 配置已检查，部署使用独立 Nginx server，不覆盖原站点。
- 根分区约 `43G`，检查时使用率约 `95%`，剩余约 `2.5G`。本次没有删除未知文件，部署采用本地构建产物和生产依赖以控制空间占用。
- 服务器已有的证书不覆盖两个 MCP 子域名，因此通过现有 HTTP-01 webroot 申请了新证书；没有修改 Cloudflare DNS。

具体部署结果、配置位置和验证记录见下一节。

## 8. 本次实际部署结果（2026-08-30）

本次已按单用户私人服务范围执行服务器部署，目标服务器为 `104.168.43.20`。Cloudflare DNS 未修改。

### 9.1 服务器与代码

- 代码已从当前工作区部署到 `/opt/mcp`，当前发布目录通过 `/opt/mcp/current` 指向；未上传 `.env`、凭据、`auth.json`、运行时 `data`、`node_modules` 和 `.git`。
- 服务器为 Ubuntu 24.04、Node.js 22；服务器仅安装生产依赖，TypeScript 在本地构建后上传 `dist` 产物，避免在根分区高使用率时额外安装开发依赖。
- 两个包已区分 `dev`（保留 `tsx --watch`）和生产 `start`（`node dist/index.js`），并声明 ESM 包类型。
- 两个 HTTP 服务均已改为只监听 `127.0.0.1`，Node 端口不直接暴露公网。
- 根分区检查时约 95% 使用率、剩余约 2.5G；本次未删除未知文件。部署后仍需持续控制发布目录和依赖占用。

### 9.2 进程与运行数据

- 小蚕：`mcp-xiaocan.service`，systemd 管理、开机启用，监听 `127.0.0.1:7788`，工作数据目录为 `/var/lib/mcp/xiaocan/data`。
- 天气：因当前工作区及环境示例中没有真实 `APPCODE`，`mcp-weather.service` 已安装但保持停止/禁用，未使用猜测值启动。
- 小蚕真实登录凭据未提供；未创建或上传 `auth.json`，服务可以启动并提供本地流程工具，需登录凭据的 API 工具保持未登录状态。
- 天气代码中的上游 TLS 兼容逻辑按已确认决定保留，未扩大关闭 TLS 范围；天气服务尚未因缺少 APPCODE 启动验证。

### 9.3 Nginx、HTTPS 与鉴权

- 新增独立配置 `/etc/nginx/sites-available/mcp-sse`，仅使用 `weather.zhoukailian.wiki` 和 `xiaocan.zhoukailian.wiki`，未覆盖 Halo、OpenClaw 或既有站点。
- Nginx 分别反代到 `127.0.0.1:7777` 和 `127.0.0.1:7788`，配置了 HTTP/1.1、`proxy_buffering off`、`proxy_cache off`、`proxy_request_buffering off`、86400 秒读写超时，并转发 `/mcp` 与 `/mcp-messages`。
- 相关旧配置在服务器 `/etc/nginx/backups/<部署时间>/` 备份。
- 已通过现有 HTTP-01 webroot 申请合并证书：`/etc/letsencrypt/live/weather.zhoukailian.wiki/`，覆盖两个子域名，未切换 DNS；Certbot 已安排自动续期。
- 由于代码没有内置鉴权，Nginx 使用服务器本地生成的 Bearer 令牌保护两个子域名。令牌只保存在 `/etc/mcp/access-token`（权限 `600`）及 Nginx 服务器配置中，未写入仓库、文档或命令示例；当前不是无保护公网服务。

### 9.4 已完成验证

- 本地 `pnpm typecheck`、两个包的本地 `build` 均通过。
- 未带 Bearer 令牌访问两个 HTTPS `/mcp` 均返回 `401`。
- 带令牌访问 `https://xiaocan.zhoukailian.wiki/mcp` 返回 `200 text/event-stream`，收到 endpoint 和连接通知，长连接可保持。
- 带令牌访问小蚕 `/mcp-messages?sessionId=...` 发送 MCP `initialize` 返回 `202 Accepted`，SSE 收到协议版本、能力和服务信息响应。
- 无会话消息 POST 被拒绝；未调用抢单、提交订单等有真实副作用的小蚕工具。
- 小蚕 systemd 服务已完成一次重启验证并恢复运行；天气服务因缺少 APPCODE 未启动。

### 9.5 剩余问题与边界

- 需要用户在服务器受保护环境变量 `/etc/mcp/weather.env` 中提供真实 `APPCODE` 后，才能启用天气服务并验证天气上游请求；不应通过聊天、Git 或日志传递该值。
- 需要用户通过受信任的方式提供小蚕真实凭据，之后再决定是否通过 `xiaocan-login` 写入服务器 `/root/.xiaocan-mcp/auth.json`；当前不应调用抢单和提交订单工具。
- MCP 服务仍是单进程单共享传输引用模型，不宣称支持多用户、多客户端并发；SSE 会话隔离和重连仍需后续代码改造。
- Cloudflare Access 未配置（本次没有 Cloudflare 账号权限），当前使用 Nginx Bearer 令牌；客户端必须安全保存令牌并按需轮换。
- 当前天气域名的授权请求在天气进程启动前不能完成有效链路验证；天气服务启动后需重复本地、外部 HTTPS、SSE 初始化和天气只读调用验证。

## 9. 已执行后的后续事项

以下事项不是本次部署前置决策，而是后续补齐项：

1. 用户侧安全保存服务器 Bearer 令牌，并将 MCP 客户端切换到远程 SSE 地址。
2. 提供真实天气 `APPCODE` 后启用天气服务并完成天气上游只读验证。
3. 如需小蚕 API 能力，通过受信任方式提供凭据后再写入服务器受保护存储。
4. 后续决定是否进行会话隔离、断线重连、限流、健康检查和结构化审计改造。



## 10. 完成定义

只有以下条件全部满足，才认为“已经从 stdio 改成服务器 SSE”：

- [ ] 两个服务都已部署到服务器。
- [ ] 两个服务都有可访问的 HTTPS SSE 地址。
- [ ] MCP 客户端已改为使用远程 SSE 地址。
- [ ] 客户端不再依赖本地 MCP 启动命令。
- [ ] 天气服务恢复正常 TLS 证书校验。
- [ ] 生产启动不再使用 `--watch`。
- [ ] 服务器已配置身份验证。
- [ ] SSE 长连接和消息转发验证通过。
- [ ] 会话、凭据和运行数据边界已确认。
- [ ] 已完成至少一次服务重启和客户端重连验证。
