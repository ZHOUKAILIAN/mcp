# 仓库治理与变更规则

## 1. 文档体系

本仓库统一使用五层文档：

- 第一层：产品定义。
- 第二层：产品实现。
- 第三层：项目落地。
- 第四层：仓库治理。
- 第五层：本地开发。

废弃文档已删除，不再作为活动真理源。

## 2. 真理源优先级

发生冲突时按以下规则处理：

1. 产品“应该是什么”：看第一层。
2. 代码“现在是什么”：看第二层和源码。
3. 项目“默认怎么运行”：看第三层和 软件包 配置。
4. 协作“如何变更和验证”：看本层。
5. 当前机器“如何继续工作”：看第五层；第五层不能覆盖前四层。

产品定义和当前实现不一致时，必须显式记录 漂移，不得只改文档掩盖代码事实。

## 3. 变更路由

开始任何功能、修复或部署改造前，先判断：

| 变更类型 | 需要同步的层级 |
|---|---|
| 新增或改变用户能力、业务流程、操作边界 | 第一层 + 第二层 |
| 纯实现重构、错误修复、依赖调整 | 第二层；若改变启动/部署则同步第三层 |
| 启动命令、环境变量、部署方式变化 | 第三层 |
| 分支、验证、发布、密钥和安全流程变化 | 第四层 |
| 本机临时脚本、开发数据、会话恢复 | 第五层，不升级为正式规范 |

## 4. 最小验证门禁

提交代码前至少执行：

```bash
pnpm typecheck
git diff --check
git status --short
```

涉及启动或传输层时，还应验证对应服务能够监听预期端口，并确认没有把 `.env`、`data/`、`auth.json` 等运行时数据纳入提交。

涉及小蚕接口或写操作时，还应检查：

- 是否明确说明操作是用户主动触发；
- 是否避免把 token、设备 ID、响应中的敏感字段写入日志；
- 是否有重复调用和失败重试风险；
- 是否更新第一层产品边界和第二层实现基线；
- 是否确认部署仍属于受限单用户服务。

## 5. 安全红线

- 不提交真实 AppCode、token、用户 ID、设备 ID 或 auth 文件。
- 不在日志中打印认证头和完整第三方响应。
- 不为了绕过错误关闭 TLS 验证、登录检查、风控或速率限制。
- 不把未授权的个人账户能力默认包装成公共多用户服务。
- 不把第五层临时材料升级成产品定义或共享治理规则。
- 不把历史计划当成当前实现依据。

## 6. 文档维护规则

- 修改产品能力时，先更新第一层，再更新第二层和代码。
- 修改代码行为时，第二层必须保持与代码一致。
- 修改部署方式时，第三层必须同步。
- 修改流程门禁时，只更新第四层，不把流程要求塞进产品文档。
- 当前机器上的临时信息只进入第五层或被忽略的运行目录。
- 已废弃文档直接删除，不保留为活动规范。

## 7. 发布前检查

- [ ] 产品定义和代码能力一致，或已记录明确 漂移。
- [ ] 软件包 启动命令和部署文档一致。
- [ ] `pnpm typecheck` 通过。
- [ ] 敏感配置由 密钥 注入，不在仓库中出现。
- [ ] 远程 HTTP 服务具备 HTTPS 和鉴权。
- [ ] 会话、用户和数据存储边界已确认。
- [ ] 小蚕 API 授权与服务条款风险已确认。
- [ ] 回滚、日志和备份方案已确认。
