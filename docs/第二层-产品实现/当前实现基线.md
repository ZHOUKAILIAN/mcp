# 当前产品实现基线

## 文档状态

- 状态：当前代码事实
- 真理源：对应软件包下的源码、`package.json` 和实际验证结果
- 规则：本文描述“现在代码做什么”，不替代第一层的产品意图

## 1. 软件包结构

```text
packages/weather-mcp/
packages/xiaocan-workflow-mcp/
```

两个软件包都使用 TypeScript、Node.js、Express 和 MCP SDK 的 SSE 传输层。当前仓库源码已经实现 HTTP SSE 启动入口，但仓库内没有 MCP 客户端配置；从实际使用方式看，目前仍是通过 `stdio` 启动或接入，服务器 SSE 尚未完成正式接入。

## 2. 天气 MCP 实现

### 启动链路

```text
packages/weather-mcp/src/index.ts
  -> 读取 APPCODE
  -> 创建 `WeatherMcpServer`
  -> startHttp(PORT || 7777)
```

### 工具

#### `get-weather`

- 输入：`cityName`，默认“杭州市”。
- 先调用城市搜索获取城市 ID。
- 再调用天气 API 获取 24 小时数据。
- 以 MCP 文本内容返回 JSON。

### 主要实现文件

- `src/server.ts`：MCP 服务、工具注册、HTTP SSE。
- `src/api/weather.ts`：天气业务客户端。
- `src/api/request.ts`：上游 HTTP 请求。
- `src/api/type.ts`：天气 API 类型。
- `src/index.ts`：启动入口。
- `src/api/test-cityid.ts`：临时测试脚本，不属于正式服务入口。

### 当前兼容性例外

- `src/api/request.ts` 当前设置了 `NODE_TLS_REJECT_UNAUTHORIZED=0`。
- 原因不是 Node.js 不支持 HTTPS，而是 `aliv18.data.moji.com` 当前返回的证书域名与访问域名不匹配，Node.js 22 会报 `ERR_TLS_CERT_ALTNAME_INVALID`。
- `ssch.api.moji.com` 在正常证书校验下可以访问。
- 这是临时兼容性例外；当前代码使用的是进程级全局关闭方式，后续应改成只影响确实有问题的单个上游请求。
- `src/api/test-cityid.ts` 曾包含硬编码 AppCode，不得作为正式脚本继续保留真实值。

## 3. 小蚕 MCP 实现

### 启动链路

```text
packages/xiaocan-workflow-mcp/src/index.ts
  -> 加载 .env
  -> 创建 `XiaocanWorkflowMcpServer`
  -> AuthStore.load()
  -> startHttp(PORT || 7788)
```

### API 工具

| 工具 | 当前行为 |
|---|---|
| `xiaocan-login` | 保存 token、userId、silkId、cityCode |
| `xiaocan-login-status` | 返回当前登录状态，不返回 token |
| `xiaocan-search-stores` | 按坐标或关键词搜索活动店铺 |
| `xiaocan-get-promotion-detail` | 查询活动详情 |
| `xiaocan-grab-order` | 调用抢活动名额接口 |
| `xiaocan-get-orders` | 查询返现订单列表 |
| `xiaocan-search-address` | 查询地址、坐标和城市代码 |
| `xiaocan-submit-order` | 提交返现/评价文字和图片链接 |

### 流程工具

| 工具 | 当前行为 |
|---|---|
| `create-workflow` | 创建 JSON 流程记录 |
| `list-workflows` | 列出记录，可按状态过滤 |
| `get-workflow` | 按 ID 获取记录 |
| `update-workflow` | 更新记录字段 |
| `advance-workflow` | 按状态规则推进记录 |
| `next-action` | 返回当前状态对应的手动建议 |
| `review-notes-draft` | 根据真实体验输入生成评价草稿 |

### 主要实现文件

- `src/server.ts`：工具注册和 HTTP SSE。
- `src/api-client.ts`：小蚕 RPC 地址、请求头、签名和 API 方法。
- `src/api-types.ts`：小蚕 API 数据类型。
- `src/auth.ts`：环境变量和 `auth.json` 凭据加载/保存。
- `src/storage.ts`：JSON 流程存储。
- `src/types.ts`：流程数据模型和状态机。
- `src/index.ts`：启动入口。

### 认证事实

认证来源按以下顺序加载：

1. 环境变量：`XIAOCAN_TOKEN`、`XIAOCAN_USER_ID`、`XIAOCAN_SILK_ID` 等。
2. `~/.xiaocan-mcp/auth.json`。

`api-client.ts` 使用的关键请求字段包括：

```text
X-Sivir
X-Vayne
x-Teemo
X-Ashe
X-Nami
X-Garen
```

当前认证和接口状态均为进程级全局状态，不是多租户实现。

## 4. 当前传输实现

两个服务都提供：

```text
GET  /mcp
POST /mcp-messages
```

当前源码使用 `SSEServerTransport`，每个服务只保存一个传输层引用。也就是说，代码层已经有 HTTP SSE 能力，但仍是单连接、开发版实现。当前实际客户端接入方式仍按 `stdio` 处理；切换到服务器 SSE 还需要补充远程客户端配置、身份验证、会话管理和部署配置。

## 5. 数据存储实现

小蚕流程默认写入：

```text
resolve(process.cwd(), "data", "workflows.json")
```

格式：

```json
{
  "workflows": []
}
```

当前没有数据库、并发锁、多实例协调或租户字段。

## 6. 从 stdio 切换到服务器 SSE

后续切换应分为以下几步：

1. 保留两个服务的独立 HTTP 端点，确认 `/mcp` 和 `/mcp-messages` 能够稳定通信。
2. 为每个服务增加服务器部署配置和固定进程启动方式，去掉生产环境对 `tsx --watch` 的依赖。
3. 在反向代理后启用 HTTPS 和客户端身份验证。
4. 修复当前单个共享传输层引用的问题，按会话管理连接，或迁移到更适合远程多会话的传输方式。
5. 将客户端配置从本地 `stdio` 启动命令改为服务器 SSE 地址。
6. 完成连通性、会话隔离、断线重连和错误处理验证后，再把 SSE 作为默认接入方式。
